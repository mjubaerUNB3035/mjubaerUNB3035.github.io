Flagship · SecurityPublic on GitHub

WatchTower: security event monitoring with AI triage

A monitoring platform built in phases, like a real product. It stores and searches security events, raises alerts from detection rules, deduplicates them, and triages each alert with a local AI agent (Ollama, llama3.1:8b) that works from code-counted facts and a decision table, not guesses. A human review flow lets an analyst approve or correct a verdict, and past corrections feed future prompts. The newest phase adds a React SOC dashboard fed by a FastAPI gateway: overview counts, an alert queue, an alert detail page where verdicts are approved or corrected, incident case files, an auto-built shift log, and hosts and users baselines, so a full shift can be worked from the browser.

34 tests passing 41 events and 6 alerts in the live dataset 6 page React dashboard: review and incidents in the browser Password spraying detection proven live Dedupe verified after a real BIGINT fix

Built for hiring managers to inspect: the repository is public, and each phase shipped with its own tests.

AI style used in WatchTower: local, tool-assisted triage agent with human review

  • Agent pattern: a single triage agent that receives a packed case, works through it, and returns one structured verdict: true_positive, false_positive, or needs_more_info.
  • Decision-table prompting: facts are counted in code first, then the prompt gives the model a decision table to judge against, so the verdict is grounded, not guessed.
  • Local LLM deployment: Ollama with llama3.1:8b, running locally with no paid API. The agent logic is kept separate from the model provider, so it can be swapped for a hosted or cloud model when a project needs that.
  • Human-in-the-loop: an analyst can approve or correct each verdict, and past corrections are fed into future prompts so the agent improves from review.
  • Guardrails in code: the model output is parsed and validated in code, and a poor answer returns needs_more_info instead of crashing or inventing a verdict.

Still growing: WatchTower was built in phases on purpose, and the planned next phase is a live attack lab: staged attack scenarios run against the system to prove detection and triage end to end. Broader detection coverage and more alert types can follow the same pattern.

Agentic AI: the styles I use

I do not just call an AI model and show the reply. I integrate agents into software: they hold state, use tools, follow clear stop conditions, and produce output that code can check. These are the styles behind my work, in plain terms for hiring managers.

ReAct pattern

Reason, act, observe, repeat

The agent reasons about the task, takes one action, observes the result, and decides the next step. It runs in a loop with named stop conditions, so it finishes, asks for more information, or hands over instead of looping forever. This is the core pattern in my agent builds, with an AgentState object tracking the case through every step.

Tool-using agents

Agents that use real tools

Instead of the model guessing everything, the agent calls tools through a registry and executor: gather information, query data, count facts, then judge. In WatchTower, intel gathering and event lookup happen in code before the model sees the case, which keeps the AI grounded in real data.

Structured prompting

Decision tables and validated output

I design prompts with a system role, a packed context, and a decision table, and I require a structured answer back. Code then parses and validates that answer. If the output does not match the allowed verdicts, the system asks for more information rather than accepting a made-up result.

Human-in-the-loop

Human review that teaches the agent

For work that matters, a person stays in charge. In WatchTower, analysts approve or correct the agent verdict, only pending verdicts can be reviewed, and those corrections are stored and fed into future prompts. That feedback loop is how an agent gets better without retraining a model.

Local and cloud ready

Local LLMs, provider-swappable design

WatchTower runs fully local with Ollama and llama3.1:8b, so it works offline and needs no paid API. I keep the model provider separate from the agent logic, the same swappable provider approach I use for data in Zenith, so an agent can move to a hosted or cloud model when scale, cost, or a client setup calls for it.

Knowing the boundary

AI where it helps, rules where they are better

Zenith is deliberately rules-based, not AI: fixed strategies, counted results, no model judgement. Knowing when an agent adds value, and when plain tested code is the right tool, is part of knowing AI well.
